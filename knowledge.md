# Particle System Knowledge Base

## 🍞 Baking & Optimization Workflow

This project uses a "Hybrid Loading" strategy for the particle system (`points.js`). 
Most static data is **baked** into a binary file (`points_data.bin`), while deterministic data (grids, colors, normals) is **generated** at runtime to save bandwidth.

### 1. When to Re-Bake?
You must re-bake `points_data.bin` if you change:
*   **Point Count**: Changing `POINT_COUNT` in `points.js`.
*   **Source Models**: Changing the `.glb` files (e.g., `allstars_walking4_points.glb`) affects the target positions.
*   **Morph Targets**: Adding or removing morph targets (attributes like `aTargetPos` for new states).
*   **Big Dipper**: Changing the star coordinates or texture mapping logic for the Constellation state.

### 2. How to Bake & Optimize
The `points.js` class contains a hidden tool `optimizeAndBake()` that processes the current live particles and exports the optimized binary.

**Steps:**
1.  Load the application normally (with the *old* or *temp* data).
2.  Open the Browser Console.
3.  Run the command:
    ```javascript
    pointsApp.optimizeAndBake()
    ```
4.  **Wait** for the logs. You will see:
    *   `Skipping Pruned Attribute: aTargetPos` (and others)
    *   `Optimizing position: Float32Array -> Uint16Array` (Compression)
    *   `⚡ PRUNED & OPTIMIZED! Size: X.XX MB`
5.  A file `points_data_optimized.bin` will download automatically.
6.  Rename this file to `points_data.bin`.
7.  Replace the existing file in your `models/` directory.

### 3. Optimization Logic (Under the Hood)
*   **Pruning**: We DO NOT save `aTargetPos` (Grid), `Normals`, `Colors`, or `SkinWeights` to the file. These are regenerated by `points.js` in milliseconds when the app starts.
*   **Color Patching**: Since `Colors` are pruned (defaults to white), `points.js` contains a specific logic inside `createBackgroundParticles` to **manually re-apply Big Dipper brightness** during the hydration phase. This ensures the constellation looks correct despite the binary file being generic.
*   **Compression**:
    *   **Positions**: Converted from `Float32` (4 bytes) to `Half-Float/Uint16` (2 bytes).
    *   **Randoms/Indices**: Converted to `Uint8` or `Uint16`.

### 4. Troubleshooting
*   **Particles look "blocky" or "snapped"?** The Half-Float compression might be too aggressive. Revert the `optimizeAndBake` logic to use Float32 for `position`.
*   **Crash on Load?** If `points.js` tries to regenerate attributes that match an *old* Point Count, it might crash. Ensure `POINT_COUNT` constant matches the baked file size.

## ⚡ CSS Performance & WebGL Co-existence Rules

> **Critical Discovery (2026-02-24):** CSS is NOT performance-neutral when a Three.js WebGL canvas is running. Certain CSS properties cause browser repaints that compete directly with the WebGL render loop and can drop FPS by **15+ frames**.

### 🔴 FORBIDDEN CSS Patterns (Never use when WebGL is active)

These properties trigger **CPU repaints** and must NEVER be used in `animation` or `transition` on always-visible elements:

| Property | Why It Kills FPS | Safe Alternative |
|---|---|---|
| `backdrop-filter: blur()` | Forces browser to sample & blur the **entire WebGL canvas** behind it every frame | Remove it. Use solid/opaque background instead |
| `filter: brightness()` animated | CSS `filter` is not GPU-composited — repaints the element + stacking layer | Use static `filter` only, never animate |
| `transition: filter` | If a JS CSS variable triggers this, it repaints on every `requestAnimationFrame` | Remove the transition; use `color` or `opacity` instead |
| `transition: all` | Watches ALL properties including non-composited ones — silent perf killer | Specify explicit: `transition: opacity 0.3s, transform 0.3s` |
| `text-shadow` inside `@keyframes` | Not GPU-composited | Keep `text-shadow` static, animate `opacity` only |
| `box-shadow` inside `@keyframes` | Not GPU-composited despite perception | Animate `opacity` or `transform` instead |
| `border-color` inside `@keyframes` | Triggers style recalculation every frame | Animate `opacity` only |
| Rapid animations `< 0.5s` cycle, `infinite` | Constant compositor thrashing | Minimum `1.5s` cycle length |

### ✅ SAFE CSS Patterns (GPU-composited, zero repaint)

Only **`opacity`** and **`transform`** are truly GPU-composited in all browsers:

```css
/* ✅ SAFE — GPU Layer, Zero Repaint Cost */
@keyframes safeAnimation {
    0%,  100% { transform: scale(1.00);  opacity: 0.85; }
    50%        { transform: scale(1.02);  opacity: 1.00; }
}
```

### 🧪 Diagnostic Steps (If FPS Drops Again)

1. Chrome DevTools → **Rendering** tab → Enable **"Paint Flashing"**  
   → Green flashing = areas being repainted every frame = culprit
2. Also enable **"Layer Borders"** → orange = GPU composited, blue = composited scroll
3. Search CSS files for: `filter:`, `backdrop-filter:`, `transition: all`, `text-shadow` inside `@keyframes`
4. Check if JS is updating a CSS variable that has a `transition` on a non-compositable property
